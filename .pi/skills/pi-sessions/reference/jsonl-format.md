# JSONL Format

The on-disk session file is JSON Lines: one JSON object per line. The first line is a `SessionHeader`; every subsequent line is a `SessionEntry`. Entries form a tree via `id` / `parentId`. All cites against `packages/coding-agent/src/core/session-manager.ts` at pi-mono `HEAD` on the date this file was written. Reference doc with prose: `packages/coding-agent/docs/session-format.md`.

`FileEntry` at `session-manager.ts:150` is `SessionHeader | SessionEntry` — the union actually written to disk.

## buildSessionContext walk

`buildSessionContext(entries, leafId?, byId?)` at `session-manager.ts:315-422` is the single function that turns the on-disk tree into the message list the LLM sees.

Algorithm:

1. **Resolve leaf** (`:328-340`). `leafId === null` → empty result (`{ messages: [], thinkingLevel: "off", model: null }`). `leafId` set → look up; not found → fallback to last entry. No leaf at all → empty.
2. **Walk leaf-to-root** via `parentId` chain, then reverse to root-to-leaf order (`:342-348`).
3. **Extract settings** while walking (`:350-362`): pick up the latest `thinking_level_change`, `model_change`, or assistant-message-derived model. Find the last `compaction` entry on the path.
4. **Emit messages** (`:364-419`):
   - **No compaction**: walk path, call `appendMessage(entry)` per entry. Only `message`, `custom_message`, and `branch_summary` (with non-empty summary) produce LLM messages; everything else is silently dropped (`:380-388`).
   - **With compaction**: emit compaction summary first (`:392`); then walk forward from the compaction's `firstKeptEntryId` up to (but not including) the compaction itself (`:396-405`); then emit everything after the compaction (`:407-411`).

This is why `custom`, `label`, `session_info`, `model_change`, and `thinking_level_change` entries are **invisible** to the LLM — they live on disk for replay but never become messages.

## Tree shape and branching

The tree is implicit: `id` / `parentId` edges form a DAG of conversation history. The `leafId` pointer (held by `SessionManager`, not on disk) marks "the current position." Branching is a first-class operation:

- **`branch(branchFromId)`** at `session-manager.ts:1125-1130` — moves `leafId` to an earlier entry. The next `appendXXX()` writes a new child of that entry, creating a divergent path. Existing entries are never modified or deleted.
- **`resetLeaf()`** at `session-manager.ts:1138-1140` — sets `leafId = null`, so the next append creates a new root. Used when re-editing the very first user message.
- **`branchWithSummary(...)`** at `session-manager.ts:1146-1167` — same as `branch()` but also writes a `branch_summary` entry capturing the abandoned path's contents.

The tree is in-place: a single `.jsonl` file holds all branches. Switching between branches just moves `leafId`; no file copy. Compare with `forkFrom` (separate file, `parentSession` link in header) — see `reference/branching-resume.md`.

## File location and naming

`getDefaultSessionDir(cwd, agentDir)` at `session-manager.ts:428-435` encodes cwd as `--<cwd-with-slashes-and-colons-replaced-by-hyphens>--` under `<agentDir>/sessions/`:

```
~/.pi/agent/sessions/--Users-bogie-code-pi-mono--/2024-12-03T14-00-00-000Z_8a3c5f1e.jsonl
```

The session-file basename is `<iso-timestamp-with-: and . replaced by ->_<sessionId>.jsonl` (constructed at `session-manager.ts:1331-1333` for forks; same scheme used by `create`). Override the sessions root via `PI_CODING_AGENT_SESSION_DIR` (`config.ts:381`); override per-call via the `sessionDir` parameter on every static factory.
