# JSONL Format

The on-disk session file is JSON Lines: one JSON object per line. The first line is a `SessionHeader`; every subsequent line is a `SessionEntry`. Entries form a tree via `id` / `parentId`. All cites against `packages/coding-agent/src/core/session-manager.ts` at the current pin (`v0.87.1`, `f07218c4`). Reference doc with prose: `packages/coding-agent/docs/session-format.md`.

`SessionHeader` at `session-manager.ts:43-50`. Not part of the entry tree (no `id` / `parentId`).

## Entry-type catalog

The discriminated union `SessionEntry` at `session-manager.ts:183-194` lists **11** entry types at `v0.87.1` (9 at `v0.85.1`; `usage` arrived in 0.86.0 and `context_edit` in 0.87.0). The order below mirrors the union; cites point to the interface definition.

| `type` discriminator | Interface | Lines | Purpose |
|---|---|---|---|
| `"message"` | `SessionMessageEntry` | `:64-67` | Wraps an `AgentMessage` (the LLM-facing message — user / assistant / toolResult / bashExecution / custom / branchSummary / compactionSummary). The actual `message` payload is shaped by pi-ai / pi-coding-agent message types; see `packages/coding-agent/docs/session-format.md` for the inner schema. |
| `"thinking_level_change"` | `ThinkingLevelChangeEntry` | `:69-72` | Records a thinking-level change. Picked up by `getSessionContextSettings` (`session-manager.ts:418-433`, the branch at `:423-424`) to set `thinkingLevel`. |
| `"model_change"` | `ModelChangeEntry` | `:74-78` | Records a `provider` / `modelId` change. Picked up by `getSessionContextSettings` to set `model` (`:425-426`). Assistant messages also imply a model change (`:427-428`). |
| `"usage"` | `UsageEntry` | `:80-89` | **New in 0.86.0.** Model-attributed usage that does **not** participate in LLM context — e.g. `kind: "cache_warm"` for prompt-cache warming requests. Carries `kind`, `provider`, `model`, `usage`, optional `note`. Appended via `appendUsage` (`:1242`). |
| `"compaction"` | `CompactionEntry<T>` | `:91-104` | Stores a `summary` of pre-compaction conversation plus `firstKeptEntryId` (the earliest entry kept verbatim) and `tokensBefore` (the pre-compaction token count). `details?: T` carries extension-specific data; `fromHook?: boolean` is `true` if generated by an extension. See `reference/compaction.md` (TBW). **Since 0.86/0.87:** optional `systemMessage` (`:103`) — the system message in force at the checkpoint, emitted ahead of the summary (`:461-464`). **Retain-none** compaction: `appendCompaction(summary, null, tokensBefore)` (`:1259`) stores the compaction's own id as its kept boundary. |
| `"branch_summary"` | `BranchSummaryEntry<T>` | `:106-116` | Created when navigating away from a branch via `/tree`. Carries `fromId` (the abandoned leaf) and an LLM-generated `summary` of the abandoned path. Same `details?` / `fromHook?` extension contract as `CompactionEntry`. Emitted by `branchWithSummary` (`:1593`). |
| `"custom"` | `CustomEntry<T>` | `:128-132` | Extension state-persistence record, **not** in LLM context. Identified by `customType`. Use to round-trip extension state across session reloads. Appended via `appendCustomEntry` (`:1288`). |
| `"custom_message"` | `CustomMessageEntry<T>` | `:159-165` | Extension-injected message that **does** participate in LLM context. Converted to a synthetic message by `sessionEntryToContextMessages` (`:453-457`, via `createCustomMessage`). `display: false` hides from TUI. Appended via `appendCustomMessageEntry` (`:1337`). |
| `"context_edit"` | `ContextEditEntry` | `:175-180` | **New in 0.87.0.** Append-only edit to one earlier entry's contribution to **model context**, leaving raw history, usage and UI untouched. `targetId` names the entry; `replacement: null` omits it, `{ content }` replaces only its content (strings become a text block for assistant / toolResult messages). Applied during projection (`projectContextEntry`, `:519-540`). Appended via `appendContextEdit` (`:1358`). **Breaking for TS consumers**: exhaustive switches over `SessionEntry` must handle it. |
| `"label"` | `LabelEntry` | `:135-139` | User-defined bookmark on `targetId`. Set `label` to `undefined` to clear. Resolved per-entry by `getLabel`. |
| `"session_info"` | `SessionInfoEntry` | `:142-145` | Session metadata; today only `name` (the display name shown in `/resume`). Set via `/name` command or `pi.setSessionName()` extension API. |

`FileEntry` at `session-manager.ts:197` is `SessionHeader | SessionEntry` — the union actually written to disk.

## buildSessionContext walk

**Restructured in 0.87.0** — `SessionManager` is now canonical for provider context. `buildSessionContext(entries, leafId?, byId?)` (`session-manager.ts:576-583`) is a thin wrapper that returns `messages` / `thinkingLevel` / `model` from `buildSessionProjection` (`:543-573`), which runs four steps:

1. **Path.** `buildSessionPath` (`:390-416`) resolves the leaf and walks leaf-to-root via `parentId`, returning root-to-leaf order.
2. **Settings.** `getSessionContextSettings` (`:418-433`) picks up the latest `thinking_level_change`, `model_change`, or assistant-message-derived model along the path.
3. **Entries.** `buildContextEntries` (`:476-512`) selects which entries participate. With no compaction on the path it returns the path. Otherwise it returns the **latest** compaction entry first, then the entries from its `firstKeptEntryId` up to but not including the compaction (skipping `system` messages; `:499-509`), then everything after it (`:510`).
4. **Projection.** Each selected entry becomes zero or more messages through `sessionEntryToContextMessages` (`:439-466`), with any `context_edit` targeting it applied first (`projectContextEntry`, `:519-540`). Only `message`, `custom_message`, `branch_summary` (with non-empty summary) and `compaction` produce messages. An older compaction retained inside the kept range contributes nothing (`:561-563`).

This is why `custom`, `label`, `session_info`, `model_change`, `thinking_level_change`, `usage` and `context_edit` entries are **invisible** to the LLM as messages. They live on disk for replay, and `context_edit` only changes how other entries project.

**Consumer consequence (0.87.0 breaking):** assigning `session.agent.state.messages` no longer changes future request history. To change it, restore with `SessionManager.inMemory(cwd, { id }, entries)`, navigate with `session.navigateTree()`, or append through `session.sessionManager` and call `session.refreshContext()`.

## Tree shape and branching

The tree is implicit: `id` / `parentId` edges form a DAG of conversation history. The `leafId` pointer (held by `SessionManager`, not on disk) marks "the current position." Branching is a first-class operation:

- **`branch(branchFromId)`** at `session-manager.ts:1572-1577` — moves `leafId` to an earlier entry. The next `appendXXX()` writes a new child of that entry, creating a divergent path. Existing entries are never modified or deleted.
- **`resetLeaf()`** at `session-manager.ts:1584-1586` — sets `leafId = null`, so the next append creates a new root. Used when re-editing the very first user message.
- **`branchWithSummary(...)`** at `session-manager.ts:1593-1618` — same as `branch()` but also writes a `branch_summary` entry capturing the abandoned path's contents.

The tree is in-place: a single `.jsonl` file holds all branches. Switching between branches just moves `leafId`; no file copy. Compare with `forkFrom` (separate file, `parentSession` link in header) — see `reference/branching-resume.md`.

## File location and naming

`getDefaultSessionDir(cwd, agentDir)` at `session-manager.ts:596-602` encodes cwd as `--<cwd-with-slashes-and-colons-replaced-by-hyphens>--` under `<agentDir>/sessions/`:

```
~/.pi/agent/sessions/--Users-bogie-code-pi-mono--/2024-12-03T14-00-00-000Z_8a3c5f1e.jsonl
```

The session-file basename is `<iso-timestamp-with-: and . replaced by ->_<sessionId>.jsonl` (constructed at `session-manager.ts:1840-1842` for forks; same scheme used by `create`). Override the sessions root via `PI_CODING_AGENT_SESSION_DIR` (`src/config.ts:290`); override per-call via the `sessionDir` parameter on every static factory.
