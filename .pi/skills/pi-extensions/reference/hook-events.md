# Hook Events

Complete catalog of pi extension hook events. Subscribe via `pi.on(eventName, handler)` from inside an extension factory; see `packages/coding-agent/src/core/extensions/types.ts:1354-1419` for the full overload list (39 overloads at `v0.87.1`). Since 0.86.0 `pi.on()` returns an unsubscribe function.

Payload **types** (the `*Event` interfaces and their `*Result` companions) are defined in `packages/coding-agent/src/core/extensions/types.ts`. Events are **emitted** from `packages/coding-agent/src/core/agent-session.ts`, `packages/coding-agent/src/core/agent-session-runtime.ts`, `packages/coding-agent/src/core/sdk.ts`, `packages/coding-agent/src/core/extensions/runner.ts`, and `packages/coding-agent/src/modes/interactive/interactive-mode.ts`. Specialized emitters (`emitContext`, `emitToolCall`, `emitToolResult`, `emitUserBash`, `emitInput`, `emitBeforeProviderRequest`, `emitBeforeAgentStart`, `emitMessageEnd`, `emitResourcesDiscover`) live in `runner.ts:~700-1060` — they wrap result merging across multiple handlers. The generic `emit()` is for fire-and-forget events; `emitGeneric` covers the cancellable `session_before_*` family.

Cites verified against pi-mono at the current pin (`v0.87.1`, `f07218c4`). **The emit-site column was fully re-derived on 2026-09-22** — the previous column had been carried across several pins by content-matching and many rows pointed at unrelated lines (e.g. `turn_start` and `message_update` both at overlapping `agent-session.ts:956-963`, which is retry-counter code). The internal `types.ts:NNN` ranges for individual events drift between releases; if a line drifts, grep for the event-type string literal (e.g. `'project_trust'`, `'session_before_compact'`) — it is unique enough to relocate quickly.

Payload: `reason: "ui_prompt"`, `kind: UIPromptKind` (`"select" \| "confirm" \| "input" \| "editor" \| "custom"`, `extensions/types.ts:827`), and optional `title`. **This is the observability hook for the classic "my extension hangs in RPC mode" failure** — see `pi-rpc`'s `reference/extension-ui-bridge.md`: an awaited `ctx.ui` call emits `extension_ui_request` and waits for a matching response, and previously a host had to *infer* that wait. Now it is announced. | `UIPromptStartEvent` (`extensions/types.ts:830-835`) | — (see ⚠ below) | `runner.ts:543`, inside `withUIPrompt` (`runner.ts:539-565`), dispatched via `emitUIPromptEvent` (`runner.ts:568-572`) |
| `ui_prompt_end` | **New in 0.85.x.** Pi is **no longer blocking** on that prompt. Same payload shape as `ui_prompt_start`, replayed from the recorded prompt so `kind`/`title` match the `start` even if state changed meanwhile (`runner.ts:551-557`). | `UIPromptEndEvent` (`extensions/types.ts:838-843`) | — (see ⚠ below) | `runner.ts:551-557` via the `finish()` closure in `withUIPrompt` |

> ⚠ **Three properties of the `ui_prompt_*` pair that determine what you can legitimately build on them.** All three follow from `withUIPrompt` (`runner.ts:539-565`) and `emitUIPromptEvent` (`:568-572`):
>
> 1. **Outermost-only, depth-tracked.** `uiPromptDepth` counts nesting; only the transition 0→1 emits `start` and only 1→0 emits `end` (`:540`, `:547-548`). **Nested `ctx.ui` calls produce exactly ONE pair, not one per call.** Do not treat these as a per-call trace.
> 2. **Balanced even on throw.** `finish()` runs from both `run().finally(finish)` and the `catch` (`:561-565`), so a prompt that rejects still emits `end`. A dangling `start` means the process died, not that the prompt is still open.
> 3. **Fire-and-forget, and NOT awaited.** `emitUIPromptEvent` wraps the emit in `queueMicrotask(() => void this.emit(event))` (`:569-571`). The handler's return value is **discarded**, and the emit is deferred by a microtask relative to the prompt actually opening. So: you **cannot cancel, block, or answer a UI prompt from these handlers** — they are notification only. Anything that needs to *intervene* belongs in the RPC `extension_ui_request` / `extension_ui_response` exchange instead.

## Cross-references

- Union of all events: `ExtensionEvent` (`extensions/types.ts:1170-1200`).
- `pi.on(...)` overload list: `extensions/types.ts:1354-1419`.
- Generic `runner.emit()` plus the cancellable `RunnerEmitEvent`/`RunnerEmitResult` machinery: `runner.ts:172` (`RunnerEmitEvent`, which excludes every event with a dedicated `emitXxx` — including, since 0.87.0, `turn_end` / `agent_before_settle`) and `:202-210` (`RunnerEmitResult`); generic `emit` at `:988`.
- `hasHandlers(eventName)` short-circuit (used everywhere to skip emit when no extension subscribed): defined on the runner and defined at `runner.ts:705` and called e.g. `agent-session.ts:532`, `:642`, `:1532`, `:1561`, `:2441`, `:2945`, `:3642`.
- Result merging is **handler-order sensitive** for: `context`, `context_with_system`, `before_provider_request`, `before_agent_start` (system prompt chained), `turn_end` / `agent_before_settle` (drafts appended in order), `cache_warming_decision`, `tool_call` (mutations chained), `tool_result`, `message_end`, `input`, `user_bash`. Read the merge logic in `runner.ts` for the exact precedence rules.
